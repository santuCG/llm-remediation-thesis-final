# Prompt v1.1 (frozen historical record)

**Status:** Superseded by v1.2. This file is a verbatim snapshot of the prompt
as it existed in `llm_reasoner.py` immediately before the v1.2 change,
captured for provenance — every scenario evidence bundle records its
`prompt_version`, so this file lets you reconstruct exactly what the model
was shown for any run tagged `v1.1`.

This is the version used for all 18 original historical scenarios and every
verification run performed during Pipeline v2.0 engineering (Fixes #1–#9).

## System prompt

```
You are a Senior DevSecOps AI Agent. Your objective is to eradicate software supply chain vulnerabilities within dependency ecosystems.
You must critically evaluate the topological subgraph. Provide comprehensive reasoning on why the vulnerability exists.
Evaluate all technically feasible remediation strategies, including native upgrades, dependency overrides, dependency resolutions, package replacement, or manual intervention. Recommend the safest strategy that preserves compatibility and explain why alternative strategies were rejected.
Do not hallucinate package versions. Recommend versions that actually exist and solve the CVE.
```

## Retry context source (retry_remediation.py, as it existed under v1.1)

```python
failure_logs = ""
log_file = f"{failure_stage}.log"
if os.path.exists(log_file):
    with open(log_file, 'r') as f:
        failure_logs = f.read()[-2000:]  # last 2000 chars, unconditional tail truncation
```

`failure_stage` at this point is always `"build"` in practice (the "Update
Metrics on Build Failure" workflow step unconditionally normalizes it to
`"build"` whenever the validate/rescan step fails, regardless of whether the
true cause was a compile error or the validator finding the CVE still
present in the rescan) — so this always read `build.log`'s last 2000
characters, regardless of which failure mode actually occurred.

## Response schema (`response_schema`, unchanged fields omitted for brevity)

```json
{
  "type": "OBJECT",
  "properties": {
    "reasoning": {"type": "STRING", "description": "Comprehensive reasoning for the strategy chosen."},
    "strategy": {"type": "STRING", "description": "The exact strategy chosen (e.g., direct_upgrade, transitive_override, dependency_resolution, replacement)."},
    "remediation_type": {"type": "STRING", "description": "Must be one of: Direct Upgrade, Transitive Override, Dependency Resolution, Replacement, Manual Review."},
    "recommended_package_version": {"type": "STRING", "description": "The specific semantic version to enforce."},
    "manifest_patch": {
      "type": "OBJECT",
      "description": "The structured intermediate representation of the manifest patch.",
      "properties": {
        "operation": {"type": "STRING", "description": "The operation to perform (e.g., 'replace', 'add_override', 'bump')."},
        "package": {"type": "STRING", "description": "The target package name to modify."},
        "constraint": {"type": "STRING", "description": "The new version constraint to enforce (e.g., '>=42.0.0' or '3.9.18')."}
      },
      "required": ["operation", "package", "constraint"]
    }
  },
  "required": ["reasoning", "strategy", "remediation_type", "recommended_package_version", "manifest_patch"]
}
```

No `enum` constraints anywhere — `strategy`, `remediation_type`, and
`manifest_patch.operation` are unconstrained strings, compliance with the
prose description is advisory only. Confirmed via `manifest_editor.py`'s own
handling logic that at least 5 distinct literal operation strings were
actually produced across historical runs: `add_override`,
`transitive_override`, `replace`, `bump`, `direct_upgrade`.
