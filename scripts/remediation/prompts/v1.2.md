# Prompt v1.2 (current)

**Status:** Active. Supersedes v1.1 — see `PROMPT_CHANGELOG.md` for what
changed, why, and the hypothesis each change is meant to test. This is the
version that will produce all 18 regenerated scenarios.

## System prompt

```
You are a Senior DevSecOps AI Agent. Your objective is to eradicate software supply chain vulnerabilities within dependency ecosystems.
You must critically evaluate the topological subgraph. Provide comprehensive reasoning on why the vulnerability exists.
Evaluate all technically feasible remediation strategies: Direct Upgrade, Transitive Override, Dependency Resolution, Replacement, or Manual Review. Recommend the safest strategy that preserves compatibility and explain why alternative strategies were rejected.
Do not hallucinate package versions. Recommend versions that actually exist and solve the CVE.
```

Changed from v1.1: the strategy list now uses the exact same 5 canonical
terms as the schema's `remediation_type` enum ("Direct Upgrade", "Transitive
Override", "Dependency Resolution", "Replacement", "Manual Review") instead
of a separately-worded description ("native upgrades, dependency overrides,
dependency resolutions, package replacement, or manual intervention").

## Retry context source (`retry_remediation.py`, v1.2 behavior)

`build_success` and `rescan_success` (already present in `metrics.json`) now
select which evidence is surfaced, since they are two different failure
modes needing different context:

- If `build_success` is false: extract lines matching an error-marker regex
  (`error TS\d`, `Error:`, `npm ERR!`, `FAILED`, `Traceback`, `error:`) plus
  2 lines of context around each, from the log named by `failure_stage`
  (in practice always `build.log`) — instead of blindly tail-truncating the
  last 2000 characters.
- If `rescan_success` is false: read `rescan.json` and, if the target CVE
  (matched the same way `validator.py` matches it — by scanner ID or via
  `relatedVulnerabilities`) is still present, summarize the package,
  installed version, and scanner-known fixed versions.
- If neither check yields anything (an uncovered failure mode), fall back to
  the v1.1 behavior (tail-truncate whichever `{failure_stage}.log` exists),
  so this never surfaces strictly less information than v1.1 did.

## Response schema (changed properties only — `reasoning`, `package`,
`constraint` are unchanged from v1.1)

```json
{
  "strategy": {
    "type": "STRING",
    "enum": ["direct_upgrade", "transitive_override", "dependency_resolution", "replacement", "manual_review"],
    "description": "The exact strategy chosen."
  },
  "remediation_type": {
    "type": "STRING",
    "enum": ["Direct Upgrade", "Transitive Override", "Dependency Resolution", "Replacement", "Manual Review"],
    "description": "The human-readable twin of strategy."
  },
  "manifest_patch": {
    "properties": {
      "operation": {
        "type": "STRING",
        "enum": ["add_override", "transitive_override", "replace", "bump", "direct_upgrade"],
        "description": "The operation to perform."
      }
    }
  }
}
```

`enum` values for `operation` match exactly what `manifest_editor.py`
already handles — nothing previously valid is excluded.
