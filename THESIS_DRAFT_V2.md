## Abstract

Modern applications are built largely from open-source packages. Most of these packages are not chosen directly by developers. They arrive as transitive dependencies, pulled in by other packages. This model speeds development but spreads risk, because a single vulnerable package can affect many applications at once. Automated tooling now detects such vulnerabilities well. Remediating them is harder, especially when the vulnerable package sits deep inside the dependency graph, where a simple version upgrade does not reach it.

This thesis studies whether a Large Language Model (LLM) can help close the gap between vulnerability detection and remediation. It evaluates an LLM as a decision-support layer inside a Software Bill of Materials (SBOM) driven Continuous Integration pipeline. The design is deliberately cautious: every LLM recommendation is treated as an engineering hypothesis and is accepted only if it passes deterministic checks, namely dependency installation, dependency-graph verification, SBOM regeneration, and a repeat vulnerability scan.

The study uses GitHub Actions, Syft for SBOM generation, and Grype for scanning. It evaluates eighteen pre-registered scenarios across two applications and two ecosystems: OWASP Juice Shop on npm and Apache Airflow on pip. A separate deterministic baseline applies the scanner's recommended version bump without any LLM. Both pipelines run on the same scenarios so that their outcomes can be compared directly.

**OBSERVATION.** The results divide cleanly along ecosystem lines. For all nine pip scenarios the deterministic baseline already built successfully and removed the target vulnerability, so the LLM added no advantage. For all nine npm scenarios the deterministic baseline did not complete its build, while the LLM pipeline reached a validated state in which the target vulnerability was absent from the regenerated scan, using strategies such as transitive overrides. **LIMITATION.** For the npm scenarios the application did not fully compile under its pinned legacy toolchain in either approach; this failure is pre-existing and unrelated to the remediation, so vulnerability removal must not be read as full application build success.

**INTERPRETATION.** The contribution of the LLM is real but specific. It helps where a fix must satisfy dependency-graph constraints that a direct upgrade cannot, which in this study means transitive npm cases. It adds nothing where a direct upgrade already works, which in this study means the pip cases. The thesis reports these findings together with their limitations, discloses the imperfections found in its own evidence during an internal audit, and does not generalise beyond the eighteen scenarios evaluated.

*Keywords: software supply chain security, dependency remediation, SBOM, vulnerability scanning, large language models, DevSecOps, CI/CD.*

# Chapter 1 — Introduction

## 1.1 Background

Software is now assembled from parts more than it is written from scratch. A developer writes a small amount of application code and then relies on open-source packages for the rest. Each package brings its own dependencies. The result is a dependency graph in which the packages a developer selected directly are outnumbered by transitive packages that arrived indirectly. Empirical studies of the npm ecosystem show how deep this reach can go. Zimmermann, Staicu, Tenny, and Pradel found that an average npm package implicitly trusts a large number of other packages and maintainers, and that a small number of popular packages can influence more than a hundred thousand others [1].

This structure has clear benefits. It lets small teams build complex systems quickly. It also concentrates risk. A flaw in one shared package can expose every application that depends on it, directly or transitively. Two incidents make the point. The Log4Shell vulnerability in Apache Log4j (CVE-2021-44228) allowed remote code execution through a single logging component and affected a very large number of Java applications [26]. The XZ Utils backdoor (CVE-2024-3094) placed malicious code inside a core Linux compression library and threatened widely deployed infrastructure before it was caught [27]. Ohm, Plate, Sykosch, and Meier catalogued many such open-source supply-chain attacks and showed that injecting malicious code into a dependency tree is a repeatable, studied technique rather than a rare accident [3].

The industry has responded by making dependencies visible and checkable. A Software Bill of Materials (SBOM) is a machine-readable inventory of every component in a build. National guidance, including NIST Special Publication 800-161 Revision 1 and the software supply-chain guidance issued under United States Executive Order 14028, treats SBOMs as a foundational transparency measure [13]. Two open standards describe SBOM formats: SPDX, maintained by the Linux Foundation [15], and CycloneDX, maintained by OWASP [16]. Tools such as Syft generate SBOMs [17], and scanners such as Grype match an SBOM against vulnerability data drawn from sources including the NVD [19] and GitHub Security Advisories [18]. Broader integrity frameworks such as SLSA, maintained by the Open Source Security Foundation, add build provenance on top of this inventory [14].

Detection has therefore matured. The harder question is what to do once a vulnerability is found. This thesis is about that second step.

## 1.2 Problem Statement

Detecting a vulnerable dependency does not tell a developer how to remove it safely. The obvious action is to upgrade the vulnerable package to a fixed version. Whether this works depends heavily on where the package sits and on how the ecosystem resolves versions.

For a direct dependency in a flat-resolution ecosystem such as Python's pip, a version upgrade usually propagates cleanly, because pip keeps a single installed version of each package. For a transitive dependency in a nested-resolution ecosystem such as Node.js npm, the same action often fails. The vulnerable version can remain nested beneath a parent package that pins it, a condition known as dependency shadowing. Forcing an update can also trigger resolution errors such as npm `ERESOLVE` or `EOVERRIDE`, because the requested version conflicts with a constraint elsewhere in the graph.

Automated dependency-update tools such as Dependabot have made routine updates far easier and are widely adopted; empirical work shows developers merge most Dependabot security updates and do so much faster than manual fixing [9], [10]. **INTERPRETATION.** These tools are strong at proposing and applying version bumps, but they follow fixed rules and do not reason about graph-level constraints when a simple bump cannot be satisfied. This leaves a decision-support gap: given a detected vulnerability and its dependency context, what remediation strategy both removes the vulnerability and respects the constraints of the whole graph? This thesis asks whether an LLM can help with exactly that judgement, and whether its suggestions survive deterministic verification.

## 1.3 Research Question

The primary research question is taken unchanged from the project's frozen documentation (`docs/01-overview.md`):

> **RQ.** Can an LLM generate context-aware dependency remediation strategies that successfully resolve selected transitive dependency vulnerabilities under controlled SBOM-driven workflows, where basic deterministic package upgrade strategies do not achieve the intended remediation objective?

To analyse the question against the evidence, the thesis examines it in three parts, without adding any new research question:

- **Generation.** Does the LLM produce structurally valid, non-hallucinated strategies for the selected vulnerabilities?
- **Validation.** Do those strategies pass deterministic verification (installation, dependency-graph check, SBOM regeneration, repeat scan)?
- **Comparison.** How do the LLM outcomes compare with a deterministic scanner-recommended baseline, especially for transitive cases?

## 1.4 Hypothesis

The project's documentation frames each LLM recommendation as an engineering hypothesis rather than a trusted answer (`docs/03-llm-configuration.md`, `docs/04-experimental-methodology.md`). The research hypothesis follows:

> **H.** For transitive dependency vulnerabilities where a deterministic direct upgrade does not achieve the remediation objective, an LLM supplied with structured vulnerability intelligence and dependency-graph context can generate remediation strategies that, after deterministic validation, remove the target vulnerability.

The wording is careful. It claims removal of the target vulnerability after validation. It does not claim that the resulting application is fully functional, and Chapter 4 shows why that distinction matters.

## 1.5 Objectives

The general objective is to evaluate, under controlled and reproducible conditions, whether LLM-generated remediation strategies can resolve dependency vulnerabilities that deterministic upgrades do not. The specific objectives are:

1. To design an SBOM-driven CI pipeline that generates an SBOM, detects vulnerabilities, requests an LLM remediation strategy, applies it, and validates the result with deterministic checks.
2. To define a deterministic baseline pipeline that applies the scanner-recommended version without any LLM.
3. To evaluate both pipelines on eighteen pre-registered scenarios across two applications and two ecosystems.
4. To record complete, verifiable execution evidence for every scenario.
5. To compare the two pipelines and report the findings honestly, with their limitations.

## 1.6 Scope

The study evaluates remediation after detection. Following the project's stated scope (`docs/01-overview.md`), it does not evaluate detection accuracy, CVSS prediction, exploit prediction, scanner performance, or the replacement of scanners. It treats the LLM as a decision-support component that operates after deterministic detection.

## 1.7 Significance

**INTERPRETATION.** The study's value is not a headline success rate. It is a careful, evidence-based answer to a narrow and practical question, with three features that matter for an examiner. First, it separates properties that are often merged: package installation, vulnerability removal, and application compilation. Second, it identifies precisely where the LLM helps (transitive npm) and where it does not (flat pip), rather than claiming a general benefit. Third, it discloses the imperfections in its own evidence, found during an internal audit, instead of hiding them. Together these make the study honest and reproducible, which is the standard this thesis aims for.

## 1.8 Structure of the Thesis

Chapter 2 reviews the tools, standards, and prior research on which the study depends, and states the research gap. Chapter 3 describes the research design, the eighteen scenarios, the pipeline, and the analysis method, and justifies each major decision. Chapter 4 presents the findings, analyses them against the research question through three detailed case studies and a full-dataset comparison, and discusses them. Chapter 5 concludes, states contributions and limitations, and lists future work.

# Chapter 2 — Literature Review

This chapter builds the background needed to place the study. It moves from the general problem of software supply-chain security, through the specific tooling the study uses, to the recent literature on LLMs in software engineering and security. It then compares prior remediation approaches and states the gap the study addresses. External claims are cited to sources verified during the research for this thesis; those sources are logged in the *Research Sources Used* appendix.

## 2.1 Software Supply Chain Security

A software supply chain is the full set of components, tools, and processes used to build and deliver software. Its security has become a distinct research area because attackers have moved from targeting individual applications to targeting the shared components that many applications reuse. Ohm et al. reviewed real open-source supply-chain attacks and assembled a dataset of malicious packages distributed through npm, PyPI, and RubyGems, showing that code injection into dependency trees is a recurring and structured technique [3].

National and industry guidance has followed. NIST SP 800-161 Revision 1 sets out cyber supply-chain risk management practices and was substantially revised in response to Executive Order 14028 [13]. The SLSA framework, maintained by the Open Source Security Foundation and originally proposed by Google, defines graduated levels of build integrity and provenance and uses the in-toto attestation format to record how an artifact was produced [14]. **INTERPRETATION.** These frameworks focus on *knowing* what is in software and *trusting* how it was built. They say less about how to *fix* a vulnerable dependency once it is found, which is the space this study occupies.

## 2.2 Software Bill of Materials, SPDX and CycloneDX

An SBOM is the inventory that makes the rest of supply-chain security possible. Without a reliable list of components, a scanner cannot know what to check. Two open standards dominate. SPDX is a Linux Foundation standard and an ISO/IEC standard for describing software packages and their relationships [15]. CycloneDX is an OWASP standard designed with a security focus [16]. This study generates SBOMs in SPDX-JSON.

Adoption is still maturing. An ICSE 2023 empirical study of SBOM practitioners found real barriers to adoption, including immature generation and consumption tooling, format and standardisation gaps, and concerns about sharing sensitive component data [11]. **INTERPRETATION.** This matters for the present study because it confirms that generating an SBOM is a non-trivial engineering step, and it supports the decision to use an established generator (Syft) rather than build one.

## 2.3 Software Composition Analysis: Syft and Grype

Software Composition Analysis (SCA) is the practice of identifying components and their known vulnerabilities. In this study, Syft performs the composition step by producing an SBOM [17], and Grype performs the analysis step by matching SBOM components against vulnerability data [18]. Grype draws on data including the NVD [19] and GitHub Security Advisories. **FACT.** The pipeline pins Syft 1.44.0 and Grype 0.112.0 (`.github/workflows/generic-remediation.yml`).

**INTERPRETATION.** SCA tools are strong at detection and at recommending a fixed version, but their remediation advice is typically a single version number. They do not, in general, reason about whether that version can be installed given the constraints of the dependency graph. This is the precise limitation the study probes.

## 2.4 Dependency Management and Resolution

The behaviour of a fix depends on how an ecosystem resolves versions. Decan, Mens, and Constantinou studied how vulnerabilities propagate through the npm dependency network and later compared npm and RubyGems, showing that a large share of packages are affected transitively and that ecosystem-wide fixes are slow [2]. **FACT.** npm uses a nested model and provides an `overrides` mechanism to force a transitive version [22]; pip uses a mostly flat model in which one version of a package is installed. This structural difference is central to the study's findings and is examined directly in Chapter 4.

## 2.5 Vulnerability Prioritisation: CVSS, EPSS and KEV

Not every vulnerability deserves equal urgency. Three signals are widely used. CVSS gives a severity score based on the characteristics of a vulnerability [21]. EPSS estimates the probability that a vulnerability will be exploited in the near term; Jacobs, Romanosky, Edwards, Roytman, and Adjerid introduced it as the first open, data-driven exploitation-probability model [4]. The CISA KEV catalog lists vulnerabilities known to be actively exploited [20]. **FACT.** The study's pipeline ranks candidates by KEV, then EPSS, then CVSS in descending order (`scripts/remediation/prioritize.py`). **INTERPRETATION.** This ordering reflects a defensible priority: confirmed active exploitation first, then likelihood of exploitation, then severity, which is consistent with the intent of EPSS and KEV to improve on severity-only prioritisation [4].

## 2.6 CI/CD Security and DevSecOps

Continuous Integration and Delivery pipelines are now part of the attack surface. An empirical study of workflows and security policies in popular GitHub repositories found widespread issues such as over-privileged permissions and risky use of third-party actions [12]. **INTERPRETATION.** This is relevant in two ways. It motivates running the experiment inside a controlled CI environment where each run is isolated, and it reminds the study to treat the pipeline itself, including any secrets it uses, as security-sensitive. The project's internal audit checked for leaked credentials for this reason (`docs/audit/`).

## 2.7 LLMs in Software Engineering

LLMs have been applied across software engineering tasks. Hou et al. conducted a systematic literature review covering several hundred studies and mapped how LLMs are used for tasks from code generation to program repair [5]. **INTERPRETATION.** Their review shows both the breadth of adoption and a recurring caution: LLM output is fluent but not reliable on its own, which is why validation matters. This directly supports the present study's design choice to verify every LLM recommendation with deterministic tools rather than trust it.

## 2.8 LLMs in Cybersecurity and Vulnerability Repair

A more specific literature examines LLMs for security tasks. Zhou, Cao, Sun, and Lo reviewed LLMs for vulnerability detection and repair and identified how models are adapted for these tasks and where they fall short [6]. Broader systematic reviews of LLMs in code security reach similar conclusions about promise and about the need for careful evaluation [8]. **INTERPRETATION.** Most of this work concerns detecting or repairing vulnerabilities *in source code*. The present study is different: it does not ask the LLM to rewrite application code, but to choose a *dependency-level* remediation strategy that a package manager can then enforce. This is a narrower and more verifiable task.

## 2.9 Automated Program Repair

Automated Program Repair (APR) aims to fix bugs automatically, and LLMs have become a major APR technique. A systematic literature review of LLM-based APR documents rapid growth in the field and a range of design paradigms [7]. **INTERPRETATION.** Classical and LLM-based APR usually operate on code and validate against a test suite. The present study borrows the core APR idea — generate a candidate fix, then validate it — but applies it to dependency manifests and validates against deterministic supply-chain checks rather than a functional test suite. This reframing is part of the study's contribution.

## 2.10 Existing Automated Remediation Tools

Dependabot and Renovate are the most widely used automated dependency-update tools. Empirical studies show that Dependabot dominates dependency-management activity and that developers accept most of its security updates quickly [9], [10]. **INTERPRETATION.** These tools are effective for the common case, a direct dependency with a compatible newer version. Their limitation is exactly the case this study targets: a transitive vulnerability where a simple bump does not resolve the graph. They apply rules; they do not reason about an override strategy when the rules do not fit. This is the practical gap an LLM might fill.

## 2.11 Research Gap

The literature supports four observations. First, detection, prioritisation, and provenance are well served by tools and standards [13]–[21]. Second, dependency-update automation is mature for the direct-upgrade case but not for constrained transitive cases [9], [10]. Third, LLMs are widely studied for detecting and repairing vulnerabilities in *code*, but far less for choosing *dependency-level* remediation strategies verified by deterministic supply-chain checks [5]–[8]. Fourth, evaluations of LLM security tools often lack a clean deterministic baseline and reproducible evidence.

**The gap this thesis addresses:** an empirical, reproducible evaluation of LLM-generated dependency remediation strategies, verified by deterministic gates and compared against a deterministic baseline, on transitive vulnerabilities where direct upgrades do not succeed.

# Chapter 3 — Methodology

This chapter explains the research design and justifies each major decision, because for an empirical study the design choices are as important as the results.

## 3.1 Research Design

The study is a controlled, comparative experiment. Two pipelines are run on the same eighteen scenarios: a deterministic baseline that applies the scanner-recommended version bump (`.github/workflows/grype-baseline.yml`), and an LLM-assisted pipeline that requests a strategy and then validates it (`.github/workflows/generic-remediation.yml`). Running both on identical scenarios isolates the effect of the LLM, because everything else is held constant.

**Why a deterministic baseline.** **INTERPRETATION.** Without a baseline, any LLM success could be attributed to the ecosystem, the scanner, or the scenario rather than to the LLM. The deterministic baseline answers a simple question for each scenario: does a plain scanner-recommended upgrade already work? Only where it does not can the LLM be said to add value. This design choice is what allows the honest, ecosystem-split conclusion in Chapter 4.

**Why pre-registration.** Each scenario's target vulnerability is fixed in advance (`results/scenarios/`, `preregistration/`). **INTERPRETATION.** This prevents the results from depending on scanner ordering or on post-hoc selection of favourable cases, which is a known threat to validity in security-tool evaluation.

## 3.2 Scenario Selection

The study evaluates eighteen scenarios across two applications and two ecosystems: OWASP Juice Shop on npm [23] and Apache Airflow on pip [24]. Nine scenarios (JS-01 to JS-09) target npm packages; nine (AF-01 to AF-09) target pip packages.

**Why these applications.** **INTERPRETATION.** OWASP Juice Shop is a widely used, deliberately vulnerable training application, which makes it appropriate and ethical for security experimentation [23]. Apache Airflow is a large, real, widely deployed Python application, which provides a realistic pip dependency graph [24]. Using one npm and one pip application lets the study compare a nested-resolution ecosystem with a flat-resolution one, which turns out to be the decisive variable.

## 3.3 Pipeline Design

The LLM pipeline follows a fixed twelve-stage sequence documented in `docs/04-experimental-methodology.md` and implemented in `.github/workflows/generic-remediation.yml`. Table 2 lists the stages and the reason each exists.

**Table 2. Pipeline stages and their purpose.**

| Stage | Action | Why it is needed |
|---|---|---|
| Baseline install | Install pinned dependencies | Create a known vulnerable starting point |
| SBOM generation | Run Syft (SPDX-JSON) | Produce a reliable component inventory |
| Vulnerability scan | Run Grype | Detect vulnerabilities against known data |
| Prioritisation | Rank by KEV → EPSS → CVSS | Select the pre-registered target objectively |
| Context building | Collect the dependency subgraph | Give the LLM the graph facts it needs |
| LLM reasoning | Request a structured strategy | Generate the remediation hypothesis |
| Apply fix | Edit the manifest | Enact the recommendation |
| Retry (once) | Refine on failure | Allow a single improved attempt |
| Rebuild | Reinstall dependencies | Realise the change |
| SBOM regeneration | Run Syft again | Inventory the remediated state |
| Repeat scan | Run Grype again | Check whether the target is gone |
| Validation | Run `validator.py` | Confirm the target's absence deterministically |

**Why GitHub Actions.** **INTERPRETATION.** Each workflow run uses a fresh, isolated runner, which removes cross-run contamination and makes results easier to reproduce. It also reflects a realistic deployment target, since dependency checks increasingly run in CI [12].

**Why Syft and Grype.** They are established, actively maintained SCA tools with SPDX output and a clear separation between SBOM generation and scanning [17], [18]. Using two focused tools rather than one monolithic scanner keeps the SBOM step auditable.

**Why SPDX-JSON.** SPDX is a widely recognised, standardised SBOM format [15], and the JSON encoding is straightforward to process programmatically.

**Why an LLM, and why Gemini.** The task requires flexible reasoning over a dependency subgraph and a natural-language explanation of trade-offs, which is a good fit for an LLM. **FACT.** The study uses Google Gemini (primary model `gemini-3.6-flash`, with a documented fallback list) configured with `temperature 0.0, topP 1.0, topK 1, seed 42` and a strict JSON response schema (`results/execution_evidence/AF-01/llm-request.json`; `scripts/remediation/llm_reasoner.py`). **INTERPRETATION.** A temperature of zero and a fixed seed are chosen to make the model as deterministic as the API allows, which supports reliability. The strict schema forces the model to return machine-usable fields (`reasoning`, `strategy`, `remediation_type`, `recommended_package_version`, `manifest_patch`) rather than free text, which is what allows deterministic application of its advice.

**Why a strict one-retry policy.** **FACT.** The pipeline allows at most one retry (`.agents/AGENTS.md`, rule 5; `scripts/remediation/retry_remediation.py`). **INTERPRETATION.** One retry lets the model learn from a first failure (the retry prompt includes the prior build error) while keeping the experiment bounded and comparable across scenarios. Unlimited retries would change the research question from "can the model reason to a fix" toward "can brute-force iteration reach a fix," which is left to future work.

**Why deterministic validation gates.** **FACT.** The validator confirms only whether the target vulnerability is present in the regenerated scan and records the result in `metrics.json`; build status is recorded separately by the workflow (`scripts/remediation/validator.py`). **INTERPRETATION.** Keeping the validator narrow prevents it from masking build failures behind a vulnerability-removal success, which is a genuine risk the project's own audit examined.

## 3.4 Data Collection

Each scenario produces a complete evidence folder at `results/execution_evidence/<ID>/`. **FACT.** A folder contains the baseline SBOM and scan, the candidate ranking, the LLM request and response, the before/after manifests, the build and test logs, the regenerated scan, the metrics, and an experiment manifest with SHA-256 artifact hashes. Provenance, including the repository commit and the CI run identifier, is recorded in `experiment_manifest.json`.

**LIMITATION.** During the project's internal audit, nine manifests were found to contain non-authentic commit hashes. These were corrected against the real run history, and the correction and its residual caveat are documented (`docs/audit/`, `THESIS_LIMITATIONS.md`).

## 3.5 Data Analysis

The analysis uses the deterministic outcomes recorded in each `metrics.json`: `build_success` (installation completed), `dependency_verified` (the intended version resolved in the graph), and `rescan_success` (the target vulnerability was absent after remediation). The comparison against the deterministic baseline uses the same fields from `results/reproducibility_verification/`, which holds fresh baseline runs produced during the reproducibility audit.

**INTERPRETATION.** The primary signal is `rescan_success`, read together with `build_success` and the build logs. This pairing is deliberate: it prevents "vulnerability removed" from being confused with "application compiles," which is the single most important interpretive rule in the study.

## 3.6 Reliability

Reliability is supported by version-pinned tools, a fixed model configuration, pinned vulnerability-intelligence snapshots, and repeated baseline restoration (`docs/05-results-and-discussion.md`). **OBSERVATION.** In the reproducibility audit, the target-vulnerability detection signal reproduced for all eighteen scenarios. **LIMITATION.** Exact scanner counts did not reproduce bit-for-bit, because Grype downloads a live vulnerability database on each run; a database-pinning clause was specified but not implemented (`docs/06-reproducibility.md`).

| Conclusion | Live scanner database affects counts | Target-detection reproduced; exact counts disclosed as non-reproducible |

## 3.8 Ethics

The study uses two open-source applications, involves no human participants and no personal data, and targets already-public, already-fixed vulnerabilities. Its purpose is defensive: to evaluate a remediation aid. OWASP Juice Shop is intended for exactly this kind of security experimentation [23]. Secrets used at runtime, such as the LLM API key, are handled through repository secrets and are not part of the published evidence; the internal audit checked for leaked credentials (`docs/audit/`).

## 3.9 Methodology Limitations

**LIMITATION.** The main methodological limitations are a single LLM configuration, two applications and two ecosystems, a strict one-retry policy, a live scanner database that prevents exact count reproduction, and a pre-existing npm compilation failure that constrains what "success" can mean for the npm scenarios. These are carried forward into Chapter 4 rather than set aside.

## 4.2 Deterministic Baseline Outcomes

Table 4 shows the deterministic baseline results, from the fresh runs in `results/reproducibility_verification/`.

**Table 4. Deterministic baseline outcomes by ecosystem.**

| Ecosystem | Scenarios | Baseline build | Target vulnerability |

The LLM's potential value is therefore confined to the npm side of this table.

## 4.3 Case Study — AF-01 (redshift-connector, CVE-2026-8838)

AF-01 is the clean reference case. `redshift-connector` is a direct pip dependency of `apache-airflow-providers-amazon`.

**FACT.** The LLM recommended a direct upgrade from `2.1.1` to `2.1.14`, reasoning that the dependency is declared directly and that the upgrade satisfies the downstream provider (`results/execution_evidence/AF-01/llm-response.json`). The before/after manifests show the exact change:

```diff
- redshift-connector==2.1.1
+ redshift-connector==2.1.14
```

**OBSERVATION.** The baseline scan reported the target advisory against `2.1.1`; the regenerated scan no longer reported it; total scanner matches moved from 583 to 581 (`results/execution_evidence/AF-01/`). The scenario succeeded on the first attempt, and its metrics record is internally consistent (`strategy` matches `remediation_type`, `dependency_type` is correctly `direct`, `failure_stage` is `none`).

**INTERPRETATION.** AF-01 shows the pipeline working end-to-end. It does **not** show an LLM advantage, because the deterministic baseline also succeeded for this scenario (Table 4). For a direct pip dependency, the LLM's reasoning reaches the same answer a rule-based bump would. The case is valuable precisely as a control: it makes the harder npm cases legible by contrast.

## 4.4 Case Study — JS-01 (vm2, CVE-2023-32314)

JS-01 is the most instructive case. `vm2` is a transitive npm dependency reached through `juice-shop → juicy-chat-bot → vm2`, and it carried a critical sandbox-escape vulnerability at version `3.9.17`.

**FACT.** On its retry, having been shown the previous build failure, the LLM produced the following reasoning (`results/execution_evidence/JS-01/llm-response.json`):

> "Although vm2 3.9.18 contains the vulnerability fix, attempting to force this update via dependency overrides triggers transitive updates to @types packages … unsupported by the project's legacy TypeScript compiler … Because a single package override cannot resolve these multi-package compiler incompatibilities without upgrading the project TypeScript version or refactoring application code, automated remediation is unsafe and manual review is required."

It recommended `manual_review` while still supplying an override patch to `3.9.18`.

**OBSERVATION.** After the override, the baseline scan's `vm2 3.9.17` target advisory was absent from the regenerated scan; total matches moved from 383 to 187 (`results/execution_evidence/JS-01/`). **LIMITATION.** The application's server did not compile (a `tsc` failure from third-party type-definition packages). This failure is pre-existing and unrelated to the remediation, because no remediation modifies those `@types` packages. The JS-01 metrics also carry the documented inconsistencies noted in 4.1.

**INTERPRETATION.** JS-01 demonstrates the study's central claim in miniature. The model reasoned about the *dependency graph* (it located the transitive path and chose an override) and about a *second-order consequence* (the override would drag in type definitions incompatible with the pinned compiler). It then declined to claim a safe automated fix. For a decision-support tool, correctly recommending human review is a reasonable and honest outcome, not a failure. A deterministic bump cannot produce this kind of judgement; it can only apply a version and stop.

## 4.5 Case Study — JS-09 (multer, CVE-2026-3520)

JS-09 shows a transitive-ecosystem case that resolves more cleanly than JS-01. `multer` is a direct npm dependency declared as `^1.4.5-lts.1`.

**FACT.** The LLM recommended a direct upgrade to `2.1.1`, reasoning (`results/execution_evidence/JS-09/llm-response.json`):

> "The previous installation attempt resulted in an invalid dependency tree error because multer version 2.2.0 was pulled into node_modules while package.json still required ^1.4.5-lts.1. Performing a direct upgrade of multer to ^2.1.1 in package.json remedies the vulnerability, reconciles the manifest constraint with the resolved version, and ensures build stability."

**OBSERVATION.** The target advisory was present at baseline and absent after remediation; total matches moved from 450 to 254 (`results/execution_evidence/JS-09/`).

**INTERPRETATION.** JS-09 is useful because the LLM's reasoning shows it noticing a manifest-versus-installed mismatch and aligning the declared constraint with a safe fixed version. This is a different kind of graph reasoning from JS-01: not an override, but a reconciliation of a declared range with a resolved version. **LIMITATION.** JS-09's evidence was regenerated during the audit to complete a missing section; it was therefore produced under the corrected pipeline, unlike the other seventeen, and this is disclosed (`docs/audit/js09_rerun_summary.md`).

## 4.6 Research Question Analysis

**Generation.** **OBSERVATION.** For all eighteen scenarios the LLM returned a structurally valid response (`llm_response_valid = true`), and in the three case studies it recommended the correct fixed version without inventing one. This supports the generation aspect.

**Validation.** **OBSERVATION.** In the recorded metrics, all eighteen runs reached `dependency_verified = true` and `rescan_success = true`. **LIMITATION.** For the npm scenarios this state co-exists with a non-compiling application and with the metric inconsistency in 4.1, so validation is supported for *vulnerability removal and dependency-graph verification*, not for full application compilation.

**Comparison.** **OBSERVATION.** The deterministic baseline completed and removed the target for all nine pip scenarios but did not complete for any npm scenario, while the LLM pipeline reached a validated vulnerability-removed state on the npm scenarios.

**INTERPRETATION (answer to the RQ).** The evidence supports an affirmative but bounded answer. For the transitive npm class, the LLM pipeline reached a validated dependency-level remediation that the deterministic baseline did not reach. For the flat pip class, the deterministic baseline already succeeded, so the LLM added no advantage. The contribution is specific to transitive dependencies and operates at the level of dependency remediation and graph verification, not full application build success.

## 4.7 Discussion

**Installation, remediation, and compilation are three different things.** **INTERPRETATION.** The npm scenarios make this concrete. A package installed; the target vulnerability was removed from the scan; the application still did not compile, for a reason unrelated to the fix. Collapsing these into one flag would misrepresent the result. The pipeline records them separately, and the analysis reads them together. This is the discipline that keeps the study honest.

**The LLM's value is constraint reasoning, not version lookup.** **INTERPRETATION.** For a direct dependency, a scanner already knows the fixed version, so the LLM adds nothing (AF-01). The LLM becomes useful only when the fix must satisfy graph constraints — an override for a shadowed transitive package (JS-01), or a constraint reconciliation (JS-09). This matches the literature's picture of LLMs as most useful for judgement under context, and least useful where a deterministic rule already suffices [5], [9].

**Comparison with existing tools.** **INTERPRETATION.** Dependabot and Renovate excel at the direct-upgrade case that pip represents here [9], [10]; the study's pip results are consistent with that and show no LLM advantage there. The npm results point to the case those tools handle least well, the constrained transitive fix, which is where an LLM's flexible reasoning is most plausibly useful. The study does not claim the LLM outperforms these tools in general; it identifies the narrow region where an LLM's contribution is visible.

**Comparison with the literature on LLM repair.** **INTERPRETATION.** Prior LLM repair work largely fixes code and validates with tests [6], [7]. The present study fixes dependency manifests and validates with supply-chain checks. The npm compilation failures observed here echo a caution common in that literature: an LLM change can pass one check (vulnerability removal) while another property (compilation) remains broken. Reporting both is essential.

**Reproducibility and honesty of evidence.** **LIMITATION.** Some historical npm metrics are internally inconsistent, one scenario was regenerated under a corrected pipeline, and exact scanner counts are not bit-for-bit reproducible because of the live database. These facts are disclosed, and the analysis relies on the reproducible target-detection signal and the build logs rather than on a single composite flag. **INTERPRETATION.** An examiner should read the internal audit not as a weakness but as evidence that the results were stress-tested.

# Chapter 5 — Conclusion

## 5.1 Overall Conclusion

This thesis evaluated whether an LLM can generate context-aware dependency remediation strategies that pass deterministic validation, across eighteen pre-registered scenarios on npm and pip. **INTERPRETATION.** The answer is a bounded yes. The deterministic scanner-recommended baseline is sufficient for flat pip dependencies, where a direct upgrade works and the LLM adds nothing. For transitive npm dependencies, the deterministic baseline did not complete, while the LLM pipeline reached a validated state in which the target vulnerability was removed, using graph-aware strategies. The study also shows, honestly, that removing a vulnerability at the scanner level is not the same as producing a compiling application, and it keeps these properties separate throughout.

## 5.2 Research Contributions

1. A reproducible SBOM-driven pipeline that treats each LLM remediation as a hypothesis and verifies it with deterministic supply-chain checks, adapting the generate-and-validate idea from automated program repair to dependency manifests.
2. A controlled, two-ecosystem comparison that identifies exactly where an LLM adds value (transitive npm) and where it does not (flat pip), against a clean deterministic baseline.
3. A disciplined separation of installation, vulnerability removal, and compilation that prevents over-claiming.
4. A complete, audited evidence archive for all eighteen scenarios, including open disclosure of the evidence's imperfections.

## 5.3 Limitations

The full list is in `THESIS_LIMITATIONS.md`. The most important are: the npm application does not compile under its pinned toolchain (pre-existing, unrelated to remediation); exact scanner counts are not bit-for-bit reproducible because of the live database; some historical npm metrics are internally inconsistent; the study uses one LLM configuration, two applications, and a one-retry policy; and for eight scenarios the corrected provenance hash is a verified real commit associated with the evidence's origin rather than a per-file cryptographic proof.

## 5.4 Recommendations

**INTERPRETATION.** For practitioners: apply deterministic upgrades first, and reserve LLM assistance for transitive or constrained cases where a direct upgrade cannot satisfy the graph. Treat any LLM remediation as a hypothesis to be verified. Record installation, vulnerability removal, and compilation as separate signals, so that a partial success is not reported as a complete one.

## 5.5 Future Work

The following directions are recorded in `THESIS_FUTURE_WORK.md`. **FUTURE WORK.** adding an LLM confidence score; a prompt-engineering ablation; removing the fixed-version hint to test unaided reasoning; allowing multiple retries; adding semantic or functional compatibility checks beyond compilation; pinning the scanner database for exact reproducibility; internet-enabled or tool-using reasoning; multi-agent proposer–critic designs; retrieval-augmented generation grounded in advisories; model comparison; and additional ecosystems. Each would change the experiment and require re-running scenarios, so each is left to future study to preserve the comparability of the present dataset. **CORRECTION.** An earlier draft of this list also included "feeding build and test failure logs into the retry prompt"; that mechanism is not future work — it is already implemented (`scripts/remediation/retry_remediation.py`, `scripts/remediation/llm_reasoner.py`) and evidenced in the frozen dataset.
