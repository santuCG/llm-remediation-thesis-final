# Experimental Methodology

This section describes the complete experimental workflow used throughout the evaluation.

Every experimental scenario follows an identical sequence of operations.

Only the scenario-specific vulnerability information changes between experiments.

The methodology is designed to ensure that remediation recommendations are evaluated using deterministic validation rather than accepted solely because they were generated by the **Large Language Model (LLM)**.

---

## Overview of the Experimental Workflow

Each experiment consists of four major phases, which are further broken down into 12 detailed stages. The exact execution ordering of these stages is deterministically enforced by the automated pipeline (see `.github/workflows/generic-remediation.yml` and orchestration scripts such as `scripts/remediation/generic_remediation.py`).

```text
Phase 1
Baseline Construction
        │
        ▼
Phase 2
Context-Aware Recommendation Generation
        │
        ▼
Phase 3
Constraint-Aware Remediation
        │
        ▼
Phase 4
Deterministic Validation
```

The output from one stage becomes the input to the next.

No stage is skipped.

---

## Stage 1 — Baseline Construction

The purpose of the first stage is to establish a reproducible baseline describing the application's dependency graph before remediation.

Every experiment begins by restoring the repository to a known deterministic state.

### Restore the Baseline

```bash
git checkout package.json package-lock.json
npm ci --ignore-scripts
```

This ensures that every experimental scenario begins from an identical dependency graph.

The resulting lockfile serves as the reference point for all subsequent comparisons.

### Generate the Baseline SBOM

A Software Bill of Materials (SBOM) is generated directly from the restored lockfile.

```bash
syft file:package-lock.json \
  -o spdx-json=baseline-lockfile-sbom.json
```
*(Example execution artifact: `results/execution_evidence/AF-01/baseline-sbom.json`)*

The lockfile is used instead of a container image because it represents only the application dependency graph.

This avoids introducing unrelated operating system packages into the experimental population.

### Generate the Baseline Vulnerability Report

The generated SBOM is analysed using Grype.

```bash
grype sbom:baseline-lockfile-sbom.json \
  -o json \
  --file baseline-lockfile-grype.json
```
*(Example execution artifact: `results/execution_evidence/JS-05/baseline-grype.json`)*

The resulting JSON report establishes the baseline vulnerability landscape for the application.

This report is never modified and serves as the experimental control throughout the evaluation.

---

## Stage 2 — Scenario Isolation

Rather than evaluating every reported vulnerability simultaneously, each experiment isolates a single predefined remediation scenario.

For every scenario, the following information is extracted:

- CVE identifier
- Package name
- Installed package version
- Recommended patched version
- CVSS severity
- Initial scanner recommendation

This information forms the deterministic input supplied to the LLM.

---

### Operational Definition: Dependency Shadowing

During exploratory experiments, an observable dependency graph behaviour was identified.

Throughout this repository, the term **"Dependency Shadowing"** is introduced as an **operational definition** describing the dependency graph behaviour observed during the evaluated experiments.

> **Dependency Shadowing** refers to the observed situation in which a direct package installation updates the root dependency while vulnerable package instances remain beneath transitive parent packages within the dependency graph.

This definition is introduced solely for describing the observed behaviour within this study and is **not** presented as an established software engineering or software supply chain security term.

---

## Stage 3 — Deterministic Baseline Remediation

Before invoking the LLM, the repository evaluates the deterministic remediation strategy implied by the vulnerability scanner.

For each scenario:

```bash
npm install <package>@<patched-version>
```

The resulting dependency graph is then inspected using:

```bash
npm ls
```

rather than relying solely on the package manager exit code.

A successful installation does not necessarily imply that all vulnerable dependency instances have been updated.

Dependency graph inspection therefore forms an essential component of the experimental methodology.

---

## Stage 4 — Threat Intelligence Enrichment

Once the deterministic baseline has been established, additional contextual information is collected.

For each experimental scenario, the following metadata is retrieved:

- EPSS score
- EPSS percentile
- CISA Known Exploited Vulnerabilities (KEV) status
- MITRE / NVD vulnerability description

This information is **not** used to identify vulnerabilities.

Instead, it is incorporated into the prompt supplied to the LLM to provide additional context for remediation strategy generation.

---

## Stage 5 — Context-Aware Recommendation Generation

The structured prompt is submitted to **Google Gemini 2.5 Flash (Google AI Studio)**.

*(Example execution artifact: `results/execution_evidence/AF-07/llm-request.json` and `llm-response.json`)*

The model receives only structured information generated during the previous stages.

The output is constrained to a predefined JSON schema.

No free-form conversational output is permitted.

Typical recommendations include:

- Direct package installation
- Dependency overrides
- No action

The generated recommendation is treated as an engineering hypothesis rather than experimental evidence.

Experimental evidence is obtained only after deterministic validation.

---

## Stage 6 — Constraint-Aware Remediation

The generated recommendation is translated into package manager operations.

### Initial Observation

During the initial experiments, the LLM-generated overrides were injected directly into the project manifest.

Package resolution terminated with:

```text
npm ERR! code EOVERRIDE
```

This behaviour was recorded as an observed experimental result.

The experiment was halted without further validation.

The observation demonstrated that npm v11 prevents overrides from replacing an existing direct dependency unless the corresponding root dependency declaration is updated simultaneously.

Rather than treating this behaviour as an LLM failure, the package manager constraint was incorporated into the experimental methodology.

---

### Constraint-Aware Injection (npm Ecosystem)

A revised remediation procedure was introduced for the npm ecosystem.

When a package recommended by the LLM already exists as a direct dependency:

1. Align the root dependency declaration with the recommended version.
2. Add the corresponding dependency override.
3. Regenerate the dependency graph.

Packages that exist only as transitive dependencies are injected exclusively through the `overrides` block.

This procedure satisfies the documented dependency resolution behaviour of npm while preserving the intended remediation strategy. For the Python ecosystem, standard `pip` resolution or direct manifest constraints are applied instead.

---

## Stage 7 — Dependency Graph Verification

Following successful package resolution, the dependency graph is inspected.

```bash
npm ls <package>
```
*(Example execution artifact: `results/execution_evidence/JS-08/package-after.json` and the corresponding Phase 4 output in `build.log`)*

The objective is to verify that the dependency graph reflects the intended remediation strategy.

Dependency graph verification is performed independently of vulnerability rescanning.

The dependency graph itself constitutes experimental evidence.

---

## Stage 8 — Runtime Integrity Verification

Successful dependency resolution does not necessarily imply successful module loading.

To provide an additional verification step, representative runtime module loading is performed.

The experiment verifies that selected modules can be imported successfully following remediation.

This stage evaluates **basic runtime module loading only**.

It does **not** constitute comprehensive functional testing of the application.

Consequently, successful module loading should not be interpreted as complete application compatibility.

*(Example execution artifact: `results/execution_evidence/AF-06/test.log`)*

> **Note on Build Failures:** Under the recorded execution of JS-09, the workflow continued to later validation stages despite a recorded build failure (see `.github/workflows/generic-remediation.yml`, `results/execution_evidence/JS-09/build.log`, `metrics.json`, and `rescan.json`). The vulnerability eradication signal functions independently of application compilation.

---

## Stage 9 — Post-Remediation SBOM Generation

Following successful dependency resolution, a new SBOM is generated from the updated lockfile.

The identical Syft version used during baseline generation is reused.

```bash
syft file:package-lock.json \
  -o spdx-json=remediated-lockfile-sbom.json
```
*(Example execution artifact: `results/execution_evidence/JS-02/rescan.json`)*

No configuration changes are introduced between baseline and remediated SBOM generation.

---

## Stage 10 — Post-Remediation Vulnerability Analysis

The regenerated SBOM is analysed using the identical Grype version employed during baseline analysis.

```bash
grype sbom:remediated-lockfile-sbom.json
```

The resulting report represents the post-remediation dependency state.

Because both reports originate from the same application population, quantitative comparison is methodologically valid.

---

## Stage 11 — Experimental Comparison

The baseline and remediated reports are compared programmatically.

The comparison evaluates:

- Total detected vulnerabilities
- Ecosystem-specific vulnerabilities
- Target CVE presence
- Target CVE absence
- Percentage change

To improve robustness, target CVEs are verified using both:

- Primary vulnerability identifiers (e.g., CVE IDs)
- Related vulnerability aliases (e.g., GitHub Security Advisory / GHSA IDs)

This prevents scanner aliasing from influencing the evaluation.

---

## Stage 12 — Experimental Interpretation

Only observations directly supported by the collected evidence are interpreted.

Examples include:

- Successful package manager execution
- Dependency graph changes
- Successful runtime module loading
- Regenerated SBOMs
- Vulnerability scanner output

Interpretations extending beyond these observations are explicitly identified as discussion rather than measurement.

This distinction is maintained throughout the accompanying Master's thesis.

---

## Validation Gates

The complete validation workflow is organised into four sequential gates.

- **Gate 1:** Generate baseline SBOMs, baseline vulnerability reports, and attempt deterministic remediation.

- **Gate 1A:** If package manager constraints prevent successful remediation, document the observed behaviour and repeat the experiment using a documented constraint-aware remediation workflow.

- **Gate 2:** Generate post-remediation SBOMs and perform a quantitative comparison against the baseline.

- **Gate 3:** Produce the final experimental summary, strictly separating:
  - Observations
  - Measured values
  - Interpretations
  - Conclusions

Only conclusions directly supported by deterministic experimental evidence are reported.

---

## Methodological Principles

The workflow documented within this repository is founded upon four methodological principles.

1. Every recommendation generated by the LLM must undergo deterministic validation.

2. Package manager behaviour is treated as experimental evidence rather than an implementation detail.

3. Dependency graph verification is performed independently of vulnerability rescanning.

4. Quantitative comparisons are performed only between equivalent experimental populations.

Most importantly:

> **The recommendation generated by the LLM is not considered experimental evidence. Experimental evidence is obtained only after successful deterministic validation through package manager execution, dependency graph verification, SBOM regeneration, and post-remediation vulnerability analysis.**

These methodological principles were applied consistently throughout all representative scenarios documented in this repository and form the foundation for evaluating the complete set of eighteen experimental scenarios presented in the accompanying Master's thesis.

**Scenario Representation Strategy:** We intentionally select representative scenarios from both Airflow and Juice Shop to demonstrate implementation across ecosystems. Do not claim universality unless every scenario has been independently verified.
