# LLM Configuration and Prompt Engineering

A central objective of this research is to evaluate whether a **Large Language Model (LLM)** can generate dependency remediation strategies when supplied with structured software supply chain evidence.

To maximise reproducibility, the LLM configuration, prompt structure, and expected output format were standardised across all experimental scenarios.

Only scenario-specific vulnerability information changes between experiments.

---

## Experimental Role of the LLM

Within this research, the LLM is **not** used to:

- Discover vulnerabilities.
- Scan source code.
- Analyse binaries.
- Retrieve vulnerability databases.
- Browse the Internet.
- Execute package manager commands.

Instead, the LLM performs a single task:

> Generate a structured dependency remediation recommendation from evidence that has already been collected by deterministic tools.

The deterministic workflow therefore remains:

```text
SBOM
    │
    ▼
Grype
    │
    ▼
Threat Intelligence
    │
    ▼
Prompt Construction
    │
    ▼
Gemini 2.5 Flash
    │
    ▼
Structured Recommendation
```

The recommendation generated by the LLM is **not considered experimental evidence**.

Experimental evidence is obtained only after deterministic validation through:

- Package manager execution.
- Dependency graph verification.
- SBOM regeneration.
- Post-remediation vulnerability analysis.

---

## Google AI Studio Configuration

All experiments were performed using **Google AI Studio**.

The configuration remained unchanged throughout the evaluation.

| Parameter | Value |
| :--- | :--- |
| **Provider** | Google AI Studio |
| **Model** | Gemini 2.5 Flash |
| **Temperature** | 0.0 |
| **Thinking Mode** | High |
| **Structured Output** | Enabled |
| **External Tools** | Disabled |
| **Internet Access** | Disabled |
| **Output Format** | JSON |

The objective of this configuration was to minimise variability in remediation decisions while ensuring that every response adhered to a predefined machine-readable schema.

---

## Why Temperature = 0?

Temperature controls sampling randomness during token generation.

A temperature of **0.0** was selected to minimise variability between repeated executions.

During repeated experiments, the following behaviour was consistently observed:

| Output Component | Behaviour |
| :--- | :--- |
| `action_type` | Stable |
| `package_name` | Stable |
| `target_version` | Stable |
| `rationale` wording | Minor lexical variation observed |

The experimental evaluation therefore considers only the structured remediation decision.

The natural-language rationale is retained solely for human interpretability and is **not** evaluated as part of the experimental outcome.

Minor wording variation within the rationale does not alter the generated remediation strategy.

## System Prompt

The following system prompt remained unchanged throughout every experimental scenario.

```text
You are an expert software supply chain security architect and automated remediation engine.

Your sole function is to analyze vulnerability details, MITRE/NVD threat mechanics, threat intelligence signals (EPSS/KEV), and dependency tree constraints to output deterministic remediation decisions.

STRICT OPERATIONAL RULES:

1. You must output NEVER anything other than a raw, valid JSON object.

2. Absolutely NO markdown formatting, NO backticks (```), NO introductory text, and NO concluding remarks.

3. Base your security rationale strictly on the provided MITRE threat mechanics, EPSS exploit probability, and the empirical structural constraints (dependency shadowing) described in the prompt.

4. Do not assume or hallucinate package behaviours outside the provided context.
```

The system prompt defines the behavioural constraints imposed on the model and remained unchanged throughout all documented experiments.

## User Prompt Template

Each experimental scenario uses the same prompt template.

Only scenario-specific values change.

The following fields are populated programmatically before each execution.

```text
You are an expert software supply chain security architect.

Your task is to remediate a software supply chain vulnerability within a modern application while considering dependency graph constraints.

Vulnerability Details

• CVE Identifier
• Affected Package
• Installed Version
• Recommended Patch Version
• CVSS Severity
• MITRE / NVD Threat Description

Threat Intelligence

• EPSS Score
• EPSS Percentile
• CISA KEV Status

Dependency Graph Context

• Observed package manager behaviour
• Observed dependency graph behaviour
• Experimental observations

Required Task

Generate the most appropriate dependency remediation strategy.

Output ONLY valid JSON matching the required schema.
```

The prompt structure remains identical across all experimental scenarios.

Only vulnerability-specific information changes.

## Structured Output Schema

Structured Outputs were enabled within Google AI Studio.

The model was constrained to return a JSON object matching the following schema.

```json
{
  "action_type": "overrides | direct_install | no_action",
  "package_name": "string",
  "target_version": "string",
  "rationale": "string"
}
```

This schema enables downstream automation to parse recommendations without requiring natural-language interpretation.

---

## Experimental Inputs

The LLM receives only structured information generated during previous experimental stages.

No external information is retrieved during inference.

Typical inputs include:

- CVE identifier.
- Package name.
- Installed package version.
- Recommended patched version.
- CVSS severity.
- MITRE / NVD vulnerability description.
- EPSS score.
- EPSS percentile.
- CISA KEV status.
- Dependency graph observations.
- Package manager behaviour.

No hidden prompts or additional context are supplied.

---

## Experimental Outputs

The generated JSON contains four fields.

| Field | Experimental Role |
| :--- | :--- |
| `action_type` | Primary decision variable |
| `package_name` | Target package |
| `target_version` | Selected remediation version |
| `rationale` | Human-readable explanation |

Only the first three fields are evaluated quantitatively.

The `rationale` field is retained solely to explain the generated recommendation and is not used as an experimental evaluation metric.

---

## Decision Variables Evaluated

This research evaluates whether the LLM selects an appropriate remediation strategy.

Accordingly, the evaluated variables are:

- Selected remediation strategy (`action_type`).
- Selected package (`package_name`).
- Selected remediation version (`target_version`).

The following characteristics are **not** evaluated:

- Writing quality.
- Explanation length.
- Stylistic consistency.
- Lexical variation within the rationale.

Consequently, two responses containing different rationale wording but identical structured decisions are considered experimentally equivalent.

---

## Why Structured Outputs?

Free-form natural-language responses introduce unnecessary variability and increase downstream parsing complexity.

Structured Outputs provide several advantages:

- Deterministic machine parsing.
- Schema validation.
- Reduced formatting variability.
- Easier integration into CI/CD automation.
- Improved reproducibility.

This design also prevents conversational artefacts from influencing the automated remediation workflow.

---

## Sources of Remaining Variability

Although a temperature of **0.0** substantially reduces sampling variability, modern LLM inference does not guarantee identical natural-language responses across repeated executions.

Minor lexical variation may still occur due to implementation details within the inference engine.

Within the documented experiments, this variation was observed only within the explanatory `rationale`.

No variation affecting the evaluated decision variables (`action_type`, `package_name`, or `target_version`) was observed.

---

## Validation Philosophy

The recommendation generated by the LLM is treated as an engineering hypothesis rather than a successful remediation.

Every recommendation must subsequently satisfy deterministic validation through:

1. Package manager execution.
2. Dependency graph verification.
3. SBOM regeneration.
4. Post-remediation vulnerability analysis.

Only recommendations that successfully complete the entire validation workflow are considered experimentally successful.

This separation between recommendation generation and deterministic validation represents the central methodological principle of the accompanying Master's thesis.
