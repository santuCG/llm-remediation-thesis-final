# LLM Configuration and Prompt Engineering

A central objective of this research is to evaluate whether a **Large Language Model (LLM)** can generate dependency remediation strategies when supplied with structured software supply chain evidence.

To maximise reproducibility, the LLM configuration, prompt structure, and expected output format were standardised across all experimental scenarios.

Only scenario-specific vulnerability information changes between experiments.

This document describes the configuration exactly as implemented in `scripts/remediation/llm_reasoner.py`, cross-verified against the actual request/response artifacts recorded in `results/execution_evidence/**/llm-request.json` and `llm-response.json`.

---

## Experimental Role of the LLM

Within this research, the LLM is **not** used to:

- Discover vulnerabilities.
- Scan source code.
- Analyse binaries.
- Retrieve vulnerability databases.
- Browse the Internet.
- Execute package manager commands.

Instead, the LLM performs a single task:

> Generate a structured dependency remediation recommendation from evidence that has already been collected by deterministic tools.

The deterministic workflow therefore remains:

```text
SBOM
    │
    ▼
Grype
    │
    ▼
Threat Intelligence
    │
    ▼
Prompt Construction
    │
    ▼
Gemini (see Model Configuration below)
    │
    ▼
Structured JSON Recommendation
```

The recommendation generated by the LLM is **not considered experimental evidence**.

Experimental evidence is obtained only after deterministic validation through:

- Package manager execution.
- Dependency graph verification.
- SBOM regeneration.
- Post-remediation vulnerability analysis.

## LLM Provider and Model Configuration

Requests are submitted directly to the **Google Generative Language REST API** (`https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`) from `scripts/remediation/llm_reasoner.py`, not through the Google AI Studio web interface.

### Model Fallback List

The pipeline attempts a sequence of models in order, moving to the next entry only if a request fails (HTTP error or exception):

```text
gemini-3.6-flash → gemini-2.5-flash → gemini-2.0-flash → gemini-1.5-flash
```

**Model actually used per scenario (recorded in each `experiment_manifest.json`):**

| Model recorded | Scenarios | Reason |
| :--- | :--- | :--- |
| `gemini-2.5-flash` | 17 of 18 (all except JS-09) | `gemini-3.6-flash` was added to the fallback list on 2026-08-01, after these scenarios' CI runs had already executed; the request fell to the next entry in the list available at that time. |
| `gemini-3.6-flash` | JS-09 only | JS-09 was regenerated after the fallback list was updated (see `docs/audit/js09_rerun_summary.md`), and the primary model responded successfully on that run. |

The model that actually responded for a given run is recorded via the `LLM_MODEL_USED` environment variable and persisted into that scenario's `experiment_manifest.json`; it should not be assumed to be the first entry in the fallback list.

### Generation Parameters

| Parameter | Value | Purpose |
| :--- | :--- | :--- |
| **Temperature** | 0.0 | Minimises sampling randomness; ensures the most deterministic and consistent output possible. |
| **topP** | 1.0 | Full probability mass considered, but combined with `temperature=0.0`, generation is restricted to the highest-probability token. |
| **topK** | 1 | Only the single top token is considered at each generation step, further enforcing determinism. |
| **seed** | 42 | Static seed to support reproducibility of results across runs. |
| **responseMimeType** | `application/json` | Forces machine-readable output. |
| **responseSchema** | see Structured Output Schema, below | Constrains the response to a fixed JSON structure. |
| **External Tools** | Not configured | No tool/function-calling capability is included in the request payload. |
| **Internet Access** | Not configured | The model receives only the structured prompt text; no retrieval or browsing capability is enabled. |

These parameters are set identically for every scenario and every attempt (first attempt and retry), in `llm_reasoner.py`'s `generationConfig` block.

## System Prompt

The following system prompt (`systemInstruction`) is sent unchanged on every experimental scenario and every retry attempt:

```text
You are a Senior DevSecOps AI Agent. Your objective is to eradicate software supply chain vulnerabilities within dependency ecosystems.
You must critically evaluate the topological subgraph. Provide comprehensive reasoning on why the vulnerability exists.
Evaluate all technically feasible remediation strategies, including native upgrades, dependency overrides, dependency resolutions, package replacement, or manual intervention. Recommend the safest strategy that preserves compatibility and explain why alternative strategies were rejected.
Do not hallucinate package versions. Recommend versions that actually exist and solve the CVE.
```

## User Prompt Template

Each experimental scenario populates the same template programmatically. Only scenario-specific values, and the retry-only failure-log section described below, change.

```text
Scenario ID: {scenario_id}
Prompt Version: v1.1

### Vulnerability Intelligence
* Target Package: {package_name}
* Vulnerable Version: {vulnerable_version}
* CVE ID: {cve_id}
* CVSS Score: {cvss}
* EPSS Probability: {epss}
* CISA KEV Status: {kev}
* Intelligence Retrieved On: {intelligence_date}
* Fixed Versions: {fixed_versions}

### Dependency Context
```json
{dependency context, e.g. npm_ls / npm_explain / package.json output}
```

Based on the vulnerability intelligence and context:
1. Recommend the safest strategy.
2. Provide the exact manifest configuration (e.g., overrides block for package.json, or line for requirements.txt) required to enforce this without breaking the build.
```

`Prompt Version: v1.1` is included in the prompt text itself, so any future change to the template is traceable directly from stored evidence.

## Retry Prompt Augmentation

When the first remediation attempt does not survive deterministic validation (see `docs/04-experimental-methodology.md`, Stage 6, and the single-retry policy in `.agents/AGENTS.md`), the pipeline invokes the LLM a second time with the same template plus one additional section inserted before the closing instructions:

```text
### Previous Attempt Failure Logs
The previous remediation attempt failed during validation/build. Please analyze these logs, refine your recommendation, and provide a new strategy.
```
{last 2000 characters of the failed attempt's build/validation log}
```
```

This is implemented in `scripts/remediation/retry_remediation.py`, which reads the tail of the prior failure log and calls `get_llm_recommendation(..., is_retry=True, failure_logs=...)`. This is the mechanism through which the LLM is informed of package-manager constraints such as `EOVERRIDE` (see `docs/04-experimental-methodology.md`, Stage 6) and revises its strategy accordingly.

*(Example execution artifact confirming this exact text: `results/execution_evidence/JS-05/llm-request.json`, which records the `EOVERRIDE` failure from attempt 1 fed back into the retry prompt.)*

## Structured Output Schema

The model is constrained, via `responseSchema`, to return a JSON object matching the following structure:

```json
{
  "reasoning": "string — comprehensive reasoning for the strategy chosen",
  "strategy": "string — e.g. direct_upgrade, transitive_override, dependency_resolution, replacement",
  "remediation_type": "string — one of: Direct Upgrade, Transitive Override, Dependency Resolution, Replacement, Manual Review",
  "recommended_package_version": "string — the specific semantic version to enforce",
  "manifest_patch": {
    "operation": "string — e.g. replace, add_override, bump",
    "package": "string — the target package name",
    "constraint": "string — the version constraint to enforce"
  }
}
```

All five top-level fields, and all three fields of `manifest_patch`, are marked `required` in the schema. This schema enables downstream automation (`scripts/remediation/generic_remediation.py`) to parse recommendations without natural-language interpretation.

*(Confirmed against real evidence, e.g. `results/execution_evidence/JS-05/llm-response.json`.)*

## Experimental Inputs

The LLM receives only structured information generated during previous experimental stages:

- Scenario ID and prompt version.
- Target package name, installed (vulnerable) version, CVE identifier.
- CVSS score, EPSS probability, CISA KEV status.
- Intelligence retrieval date (taken from the EPSS snapshot metadata).
- Known fixed version(s).
- Dependency graph context (package-manager output such as `npm ls` / `npm explain` errors, and the current manifest).
- On a retry only: the tail of the previous attempt's failure log.

No external information is retrieved during inference; no hidden prompts or additional context are supplied.

---

## Experimental Outputs

| Field | Experimental Role |
| :--- | :--- |
| `strategy` | Primary decision variable — the remediation approach selected. |
| `remediation_type` | Categorical label for the same decision (Direct Upgrade / Transitive Override / Dependency Resolution / Replacement / Manual Review). |
| `recommended_package_version` | Selected remediation version. |
| `manifest_patch` | Structured, machine-applicable representation of the manifest change (operation, package, constraint). |
| `reasoning` | Human-readable explanation, retained for interpretability. |

`strategy`, `remediation_type`, `recommended_package_version`, and `manifest_patch` are evaluated quantitatively (they determine what is actually applied to the manifest and validated). `reasoning` is retained solely to explain the generated recommendation and is not used as an experimental evaluation metric.

---

## Decision Variables Evaluated

This research evaluates whether the LLM selects an appropriate remediation strategy. Accordingly, the evaluated variables are:

- Selected remediation strategy (`strategy` / `remediation_type`).
- Selected remediation version (`recommended_package_version`).
- Selected manifest patch (`manifest_patch`).

The following characteristics are **not** evaluated:

- Writing quality.
- Explanation length.
- Stylistic consistency.
- Lexical variation within `reasoning`.

Two responses containing different `reasoning` wording but identical structured decisions are considered experimentally equivalent.

---

## Why Structured Outputs?

Free-form natural-language responses introduce unnecessary variability and increase downstream parsing complexity. Structured Outputs provide several advantages:

- Deterministic machine parsing.
- Schema validation.
- Reduced formatting variability.
- Easier integration into CI/CD automation.
- Improved reproducibility.

This design also prevents conversational artefacts from influencing the automated remediation workflow.

---

## Sources of Remaining Variability

Although `temperature=0.0`, `topP=1.0`, `topK=1`, and a fixed `seed=42` substantially reduce sampling variability, modern LLM inference does not guarantee bit-identical natural-language responses across repeated executions, and the model actually serving a request can differ across runs due to the fallback mechanism described above.

Within the documented experiments, lexical variation was observed only within the explanatory `reasoning` field. No variation affecting the evaluated decision variables (`strategy`, `remediation_type`, `recommended_package_version`, `manifest_patch`) was observed among the recorded scenarios.

---

## Validation Philosophy

The recommendation generated by the LLM is treated as an engineering hypothesis rather than a successful remediation.

Every recommendation must subsequently satisfy deterministic validation through:

1. Package manager execution.
2. Dependency graph verification.
3. SBOM regeneration.
4. Post-remediation vulnerability analysis.

Only recommendations that successfully complete the entire validation workflow are considered experimentally successful.

This separation between recommendation generation and deterministic validation represents the central methodological principle of the accompanying Master's thesis.
